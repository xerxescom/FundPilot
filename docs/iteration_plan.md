# FundPilot 下一阶段迭代计划

评估日期：2026-09-17。依据当前仓库代码、现有路线图及本地测试结果；这是实施建议，文中的修复和功能尚未执行。

## 1. 方向与现状

下一阶段目标：让 FundPilot 成为每天可依赖的个人投资复盘工具。优先保证账本、行情、指标和任务状态可信，再降低日常维护成本，最后增加研究深度。

按现有定位继续服务本地单用户，保留 FastAPI、PostgreSQL、Vue 的整体结构。近期重点投入计算正确性、数据追溯、任务恢复和日常操作体验。

已经具备的基础：

- 自选、基金详情、评分排行、组合、相关性、市场、报告、数据健康和任务中心。
- 基金净值双源兜底及重试；统一股票/ETF/基金交易账本；持仓截图确认导入。
- 默认、稳健、进攻、低回撤、同类相对评分；本地/在线 AI 与规则兜底。
- 76 项后端测试通过；前端 `npm run build` 通过，包含 TypeScript 检查。

验证边界：本次没有验证真实行情源可用性、生产 PostgreSQL 迁移、浏览器端完整操作链和线上模型。测试数据库使用 SQLite 内存库。pytest 有缓存目录写入告警；前端构建有依赖注释和大包告警。

原 `feature_roadmap.md` 的部分事项已经实现，后续应将其同步为“已完成 / 部分完成 / 待实施”，避免重复安排。

## 2. 优先修复的代码问题

以下为代码审阅结论，除现有测试外没有新增复现测试；实施时先为边界行为建立回归用例。

| 优先级 | 代码证据 | 影响 | 建议与验收 |
| --- | --- | --- | --- |
| P0 | `portfolio_service.portfolio_overview` 将未知市值按零汇总，却保留该持仓成本 | 缺行情可能被显示为亏损，仓位也可能失真 | 返回估值完整性、缺失资产和行情日期；不完整时清楚标示部分估值，整体盈亏不输出确定值；缺行情用例不得出现虚假全额亏损 |
| P0 | `create_transaction` / `delete_transaction` 先提交流水，再重建持仓 | 历史补录或删除导致重建失败时，流水与持仓可能不一致 | 流水变更和持仓重建使用同一事务；补录、删除、超卖、重建异常均验证原子性；失败后两者都不变 |
| P0 | `portfolio_drawdown_1m` 用当前份额乘历史价格，缺价直接求和，并取最后 30 行 | 当前持仓的历史模拟可能被误解为真实账户回撤；缺价产生假跌幅；窗口含义不明确 | 先明确为“当前持仓历史模拟”并修正日期对齐和缺价处理；真实账户回撤在现金流和历史持仓齐备后交付；没有交易历史的截图持仓不编造历史业绩 |
| P0 | `calculate_indicators_from_nav` 未先截断 `calc_date` 之后的数据，收益直接取单位净值变化 | 指定历史日期时可能读入未来数据；分红等事件的收益口径缺少处理 | 按截至日期过滤；区分估值净值与总收益序列；加入未来数据后历史计算结果保持不变；分红、拆分、短历史样本有明确用例 |
| P0 | `task_log_service.result_counts` 把结果总数当成功数；有子项失败仍可记 `success` | 用户看到“成功”，实际存在未处理项 | 建立 success / partial_success / failed 状态；3 项中失败 1 项必须显示成功 2、失败 1，并能定位失败资产 |
| P1 | `BackgroundTasks` 执行长任务；调度器按固定时间间隔依次启动工作 | 重启可能遗留任务；上游未完成时下游也可能运行 | 持久化任务参数、步骤、心跳与结果；按依赖推进；重启后识别中断，支持幂等重试 |
| P1 | `data_health_service` 解析截断后的日志字符串，且同步查询未包含 `queued_sync_watchlist_nav` | 后台同步状态可能漏报，长结果难以可靠追溯 | 任务结果改结构化存储并按资产查询；后台任务与前台任务健康状态一致 |

价格口径也需要明确：股票/ETF 当前抓取前复权历史并存入单一 `close` 字段。建议保存或显式区分原始价格、复权类型和计算版本，避免估值、历史收益和数据修订混用同一口径。

## 3. 分阶段交付

以下按一名熟悉项目的全职开发者粗估，总体约 6–9 周；包含关键测试，外部数据异常、账本迁移和真实样本核对可能增加时间。阶段以验收为准，不以固定日期强行切换。

### 阶段一：数值与账本可信，约 1–2 周

交付：

1. 修复上述 P0 项；完整账户回撤先做好口径隔离，后续随现金账本落地。
2. 明确交易金额是否含费用、已实现与未实现盈亏、价格/收益口径、月度窗口和 Sharpe 参数。
3. 区分“截图期初持仓”和“流水推导持仓”，设计期初余额衔接，避免截图导入后第一次新增交易覆盖已有份额。
4. 汇总接口统一输出截至日期、数据是否完整和缺失原因，前端对应展示。

验收：手算样本核对通过；缺价不生成假亏损；交易失败不留下半完成状态；历史计算不使用未来数据；现有测试和前端构建持续通过。

### 阶段二：日常更新可靠，约 1–2 周

交付：

1. 一键更新采用“行情 → 指标 → 评分 → 预警 → 报告”的依赖流程，报告包含本次预警；失败按资产隔离，未就绪资产跳过下游并说明原因。
2. 任务增加幂等键、结构化结果、进度、超时、中断状态、失败项重试和重复点击合并。
3. 拆出独立执行进程，保留现有任务 API；先按单用户实际负载决定使用数据库任务表还是既有路线图中的 Redis Worker，验收重点是持久化、恢复和幂等性。
4. 数据健康覆盖股票/ETF，按交易日与品种披露延迟判断新鲜度；新增基金档案获取失败时也能走兜底路径。
5. 将生产 PostgreSQL 的迁移检查、基础集成测试和备份恢复演练纳入交付。

验收：人为中断任务后有可见状态和恢复路径；重复提交不重复入账；失败标的可单独重试；前台和后台展示同一份结果；数据库异常不阻止记录可解释的失败信息。

### 阶段三：形成每日使用闭环，约 2–3 周

交付：

1. CSV 交易导入：字段映射、预览、金额校验、重复识别、错误行说明与导入批次追溯。先约定一种券商模板，再扩展格式。
2. 现金、出入金、分红、费用、已实现收益；基于交易及现金流形成账户历史快照和真实收益曲线。
3. 股票/ETF 自选与持仓批量行情更新，接入相同任务和数据健康链路。
4. 首页围绕“数据是否齐全 → 今天变化 → 风险原因 → 待办操作”组织；重复预警合并、支持已读及有效期。
5. 报告展示输入日期、证据数据、模型/规则来源和降级原因；点击风险能返回相关资产或任务。

验收：CSV 重复导入不重复记账；一份券商样例的份额、成本、现金及盈亏可逐项对账；从首页能完成更新、查看失败项、理解风险和阅读报告。

### 阶段四：研究深度与性能，约 2 周

交付：

1. 固化评分版本、参数和历史输入；同类排名展示样本范围及数量；把缺数据与低得分分开表达。
2. 在可追溯的历史数据上做样本外验证，确认评分稳定性；避免仅凭增加策略数量判断改进。
3. 基金重仓与直接股票持仓穿透合并，展示披露日期、覆盖比例与未知部分。
4. 对日报和基金解释建立固定评估样例，检查数字引用、过期数据、来源和规则兜底；相同输入缓存生成结果。
5. 在固定样本和机器上建立性能基线，再优化批量查询、净值批量写入和前端依赖体积。

验收：同一数据与评分版本可复现结果；评分变化可解释；穿透结果显示覆盖范围；性能优化前后使用相同数据量和缓存条件比较。

## 4. 工程优化的具体落点

| 方向 | 当前依据 | 建议 |
| --- | --- | --- |
| 后端查询 | 数据健康按基金执行多次查询，净值写入逐行查询 | 记录查询数和耗时，改批量聚合及批量 upsert；优先处理随资产数量线性增加的往返 |
| 前端体积 | 构建中入口约 1,045 kB、图表块约 1,038 kB，均为未 gzip 的产物；gzip 各约 345 kB | 路由已懒加载，进一步评估 Element Plus 与 ECharts 按需引入；以首页实际传输量和加载时间为目标 |
| 自动验证 | 现有 SQLite 测试和构建可用；未见前端测试脚本和仓库 CI 配置 | 添加 PostgreSQL 集成与迁移验证、核心操作端到端测试；优先覆盖入账、任务恢复、缺行情和导入去重 |
| 可部署性 | Compose 前端运行开发服务器，启动时安装依赖；后端健康接口只返回固定状态 | 前端使用构建产物部署；锁定依赖安装；区分存活和数据库就绪检查；迁移作为发布步骤 |
| 数据可恢复性 | 存在持久化数据库卷，但尚需证明恢复流程 | 提供备份/恢复操作说明，并在独立测试库验证份额、流水和报告数量一致 |

建议性能目标是待验证目标：在明确机器配置、50 个自选及固定历史长度的样本上，常用只读 API 的热态 P95 控制在 1 秒内；任务提交 P95 控制在 1 秒内。先采集基线，再调整目标，不将它们描述为当前实测结果。

## 6. 后置事项

新闻聚合、Embedding 语义检索、多模型自动路由、更多评分策略放在基础链路稳定之后。它们进入开发前应有明确使用场景与可检查的效果指标，例如新闻与真实持仓的关联准确率、检索结果证据可追溯率、模型增加的费用与报告质量改善。

项目下一阶段是否进步，主要看三个结果：账本能对账、每日任务能恢复、用户能知道每个数字来自哪一天和哪份数据。
